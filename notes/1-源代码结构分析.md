# DeepEP 源代码结构分析

本文基于 `E:\codex_home\code\DeepEP` 当前工作区源码整理，按树型结构列出主要文件与目录，并简要说明其职责。

## 总体结构

DeepEP 是 Python + PyTorch C++ Extension + CUDA/JIT kernel 组成的通信库：

- `deep_ep/`：Python 包入口，封装用户侧 API，例如 `ElasticBuffer`、legacy `Buffer`、测试/环境工具。
- `csrc/`：C++/CUDA 扩展源码，负责 pybind11 绑定、buffer 管理、NCCL/NVSHMEM 后端、JIT 编译和 legacy kernels。
- `deep_ep/include/deep_ep/`：运行时 JIT 编译使用的 CUDA header-only kernels 和公共工具。
- `tests/`：V2 elastic 路径、V1 legacy 路径和工具函数测试。
- `docs/`、`README*.md`：官方文档及中文翻译。
- `figures/`：文档使用的通信/overlap 示意图。

## 关键调用关系

### Python API 到 C++/CUDA

```text
用户代码
  -> deep_ep.ElasticBuffer / deep_ep.Buffer
  -> deep_ep._C PyTorch extension
  -> csrc/elastic/buffer.hpp 或 csrc/legacy/buffer.hpp
  -> csrc/kernels/... host runtime
  -> deep_ep/include/deep_ep/impls/... JIT CUDA kernels 或 csrc/kernels/legacy/*.cu
```

- V2 主线走 `ElasticBuffer`，核心文件是 `deep_ep/buffers/elastic.py` 和 `csrc/elastic/buffer.hpp`。
- V1 legacy 走 `Buffer`，核心文件是 `deep_ep/buffers/legacy.py` 和 `csrc/legacy/buffer.hpp`。
- `csrc/python_api.cpp` 是 `_C` 扩展入口，具体类和方法的 pybind 绑定分散在 `csrc/elastic/buffer.hpp` 和 `csrc/legacy/buffer.hpp`。

### V2 Elastic 路径

```text
ElasticBuffer.dispatch/combine
  -> 计算 buffer size、domain、SM/QP 数量
  -> backend/nccl.cu 创建或复用 NCCL communicator / Gin handle
  -> csrc/kernels/elastic/*.hpp 创建 JIT runtime
  -> deep_ep/include/deep_ep/impls/*.cuh 编译并 launch kernel
```

V2 的核心特点是运行时 JIT 编译、统一 `ElasticBuffer` 接口、NCCL Gin 后端和解析式 SM/QP 数量计算。

### NCCL 的含义

NCCL 是 NVIDIA Collective Communications Library，即 NVIDIA 集合通信库。它是 NVIDIA 提供的多 GPU / 多节点 GPU 通信库，常用于深度学习训练和推理中的分布式通信。

NCCL 常见通信能力包括：

- all-reduce：多卡梯度同步中最常见，把各 rank 数据规约后同步给所有 rank。
- all-gather：每个 rank 收集其他 rank 的数据。
- reduce-scatter：先规约数据，再把结果切分给不同 rank。
- broadcast：从一个 rank 向其他 rank 广播数据。
- point-to-point send/recv：点对点发送和接收。

在 PyTorch 分布式里，常见写法是使用 NCCL backend：

```python
dist.init_process_group(backend='nccl')
```

这表示 PyTorch 的 GPU 分布式通信会通过 NCCL 执行。DeepEP 的 `init_dist` 函数也是这样初始化分布式环境的。

在 DeepEP V2 中，核心通信后端从 V1 的 NVSHMEM 切换到了更轻量的 NCCL Gin。可以粗略理解为：

- 普通 NCCL：主要面向 all-reduce、all-gather、reduce-scatter 等常规 collective 通信。
- NCCL Gin：NCCL 体系里的 GPU-Initiated Networking 能力，更适合 DeepEP 这种需要 GPU 侧细粒度通信控制的 MoE dispatch/combine 场景。

一句话总结：NCCL 是 NVIDIA 的 GPU 通信库，是 PyTorch 分布式 GPU 通信的常用后端；DeepEP V2 基于 NCCL Gin 构建更贴近 MoE 专家并行的通信路径。

### QP 的含义

源码和测试中经常出现 `num_qps`、`num_allocated_qps` 这类参数。这里的 QP 通常指 Queue Pair，是 RDMA/InfiniBand 通信里的核心对象。

一个 QP 可以理解为一条 RDMA 通信通道，由两部分组成：

- Send Queue：发送队列。
- Receive Queue：接收队列。

所以它叫 Queue Pair。

在 DeepEP / RDMA / NCCL Gin 语境里，说“通信使用的 QP 数量”，大致意思是：GPU 或通信后端会使用多少条 RDMA 通信队列/通道来并行发送和接收数据。

QP 数量会影响通信性能：

- QP 太少：并行度不够，可能打不满网卡带宽。
- QP 太多：资源开销变大，调度和同步成本增加，甚至影响延迟。
- 合适的 QP 数量：能在带宽、延迟、资源占用之间取得平衡。

DeepEP V2 README 中提到 `Analytical SM & QP count calculation`，意思是 V2 可以根据 EP 规模、SM 数量、通信模式等解析计算需要多少 SM 和 QP，不再主要依赖手动 auto-tuning。

一句话总结：QP 是 RDMA 通信中的队列对，可以理解为通信通道；“通信使用的 QP 数量”就是 DeepEP 用多少条这样的通道并行搬运 token 数据。

### V1 Legacy 路径

```text
Buffer.dispatch/combine 或 low_latency_dispatch/combine
  -> legacy config 选择 intranode/internode/low-latency kernel
  -> NVSHMEM / IBGDA 初始化和通信
  -> csrc/kernels/legacy/*.cu launch 编译好的 CUDA kernel
```

V1 主要用于兼容旧接口和对比历史实现，依赖 NVSHMEM，代码集中在 `csrc/legacy/` 和 `csrc/kernels/legacy/`。
